# DT—09 / Engineering Fieldbook

**I build software for problems that deserve more than a dashboard.**

Data investigation. AI assurance. Adaptive learning. Interactive products.

My work centres on a recurring engineering question:

> What happened, why did it happen, and what evidence lets someone verify the answer?

The [interactive fieldbook](https://dt-09.github.io/DT-09/) is the full experience: project explorer, visual system maps, an interactive evidence pipeline, and direct routes into the code.

## One engineering pattern

<div align="center">

<img src="./assets/fieldbook-map.svg" width="100%" alt="Illustration of the DT—09 engineering pattern." />

</div>

`INPUTS → RULES → OBSERVATION → EVIDENCE → HUMAN DECISION`

Different domains. One consistent preference for explicit inputs, observable behaviour, traceable findings and honest limitations.

| Discipline | What I build with |
|---|---|
| Application engineering | Python · JavaScript · TypeScript · C# · React · FastAPI · .NET |
| Data and decision systems | CSV / JSON pipelines · deterministic validation · SQLite · REST APIs |
| AI assurance | Policy evaluation · acceptance protocols · trace auditing · regression testing |
| Interactive interfaces | Responsive workflows · data visualisation · Three.js · motion |
| Delivery | Git · GitHub Actions · Cloudflare Pages |

Technologies are listed because they appear in the work above—not as a claim of equal depth or production experience in every tool.

## Engineering standards

- **Evidence before assertion.** Keep source references and calculation paths close to results.
- **Deterministic where possible.** Make important checks repeatable.
- **Boundaries are part of the design.** State what a tool does not establish.
- **Human review stays visible.** Surface uncertainty and escalation points.
- **Demonstrate the real system.** Prefer runnable examples, tests and inspectable outputs to decorative claims.
